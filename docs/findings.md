# Findings

What the numbers say, in the order they matter. The retrieval table in the README is regenerated by `make eval`; the numbers quoted here are from the run named at the top of that table, and this file is rewritten after every run that changes them. Answer-quality findings are added when the judge run is in.

## 1. The reranker is the component that earns its keep

Passing the hybrid candidates through `cross-encoder/ms-marco-MiniLM-L-6-v2` is the only change in the table that moves a metric by more than a few points: on the 1,000 held-out queries it adds about 16 MRR@10 points and about 18 recall@5 points, with bootstrap intervals that sit far from zero.

The depth sweep shows diminishing returns: most of the gain is there at depth 20, depth 50 adds a few points, depth 100 adds under one point for nearly twice the rerank time. The cost is the serving question: on a GPU a depth-50 rerank takes tens of milliseconds, on a laptop CPU the same cross-encoder scores 33 to 44 pairs per second, so depth 50 costs over a second per query. The served depth on a CPU host is decided from the latency measured on that host, not from this table.

## 2. Fusion on its own adds nothing at the top of the list

Reciprocal rank fusion of BM25 and dense retrieval does not change recall@10 or MRR@10 against dense alone by an amount distinguishable from zero. What fusion adds is breadth: recall@20 rises by a few points, and that wider candidate pool is what the reranker consumes. So "hybrid" is in the system as the reranker's candidate generator, not as a retrieval mode worth serving on its own. BM25 alone reaches 55.0% recall@10.

## 3. HNSW costs a couple of points at efSearch 64, and the setting matters

Exact search over the embedding matrix is the ceiling for the dense row; the HNSW index (M = 32, efConstruction = 200) sits a little over two points below it at efSearch = 64. The sweep recovers most of that for almost nothing: efSearch 128 halves the loss at well under a millisecond per query on the evaluation machine, 256 recovers a little more. The served default is 128.

## 4. int8 storage is free in quality

Per-dimension symmetric int8 quantisation of the embedding matrix (292 MB instead of 1,166 MB) gives the same recall@10 as exact float32 search, with MRR@10 within 0.1 points even without rescoring. The served system keeps the float32 HNSW index because memory on the host is not the constraint; the row is there so that the day it is, the cost of switching is a known number.

## 5. Corpus size changes the numbers more than any model choice

On the same 200 queries, BM25 reaches 76.0% recall@10 when the corpus is the 82,326-passage subset those queries were drawn with, and 44.5% on the full 759,421 passages, a drop of 31.5 points. The dense and hybrid rows lose more than twenty points the same way. A retrieval number without the corpus size next to it is not a number. That is why every row in this project is reported on the full corpus and, wherever possible, on held-out queries.

## 6. Latency in the retrieval table is the evaluation machine's

The table's latencies come from the Colab machine: a Tesla T4 for the encoder and the reranker, two vCPUs for BM25 and HNSW. The numbers a client would see on a CPU host are measured on that host once it exists and reported in their own table.

## What changes next

- Served rerank depth: set from the CPU latency measurement, with the quality cost of each depth taken from the sweep above.
- Answer quality: generation and judge runs on `legacy200` and `unans50`, per served mode.
